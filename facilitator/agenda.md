# 02. ファシリテーターガイド (180 分)

## タイムテーブル

| 時間 | セッション | 目的 | 主担当 | 成果物 |
|---:|---|---|---|---|
| 0:00 - 0:10 | オープニング | 期待値合わせ | ファシリテーター | 当日のゴール共有 |
| 0:10 - 0:25 | 題材の現状共有 | 課題の共通理解 | ビジネスロール代表 | 現状課題リスト |
| 0:25 - 0:45 | 既存ツール観察 (ライブデモ) | 改善観点を引き出す | ファシリテーター | 観察メモ |
| 0:45 - 1:05 | ユーザーストーリー化 | 要望をストーリーに変換 | ビジネス + 開発ペア | ユーザーストーリー 1〜3 本 |
| 1:05 - 1:25 | Copilot で仕様化 | 仕様 / 受け入れ条件作成 | 開発ロール (画面共有) | 仕様ドラフト |
| 1:25 - 1:35 | 休憩 | リセット | - | - |
| 1:35 - 1:55 | 実装計画化 | 仕様 → タスク分解 | 開発ロール | 実装タスクリスト |
| 1:55 - 2:25 | プロトタイプ生成 | 動くものを作る | 開発ロール (Copilot) | 動く UI 改修版 |
| 2:25 - 2:45 | レビューと改善 | ビジネス視点でフィードバック | ビジネスロール | 改善後プロトタイプ |
| 2:45 - 3:00 | まとめ | 学びの共有と次アクション | 全員 | 振り返りメモ |

## 各セッションの進め方

### 0:00 - 0:10 オープニング

- **投影スライド**: `opening-slide.html` をブラウザでフルスクリーン表示 (F11 / プレゼンモード)。
- ワークショップの目的を 1 枚で共有する。
- 「作るもの / 作らないもの」を明確にする。
  - 作るもの: ユーザーストーリー、仕様、実装計画、簡易プロトタイプ、レビュー記録
  - 作らないもの: 本番 API 連携、認証、3D ビュー、CI/CD
- 役割を決める。
  - **ナビゲーター**: 画面共有しながら Copilot に話しかける人 (1 人)
  - **ビジネスレビュアー**: ユーザー価値の観点でレビューする人 (1〜2 人)
  - **開発レビュアー**: 仕様 / 実装観点でレビューする人 (1〜2 人)
  - **オブザーバー**: 観察しメモする人 (残り全員)
- **コンティンジェンシーの予告**: GitHub Copilot のクォータが枯渇する可能性に触れ、「Copilot が反応しなくなったら無理せず手を挙げてください。こちらから全員 BYOK 切替を案内します」と 1 分でアナウンスする。手順は `../docs/05-backup-byok.md` 参照。

### 0:10 - 0:25 題材の現状共有

- `../docs/01-theme.md` を読み合わせる。
- 参加者の経験から、現状の設置設計で困っていることを 5 つほど挙げる。
- 困りごとを後の「ユーザーストーリー化」の入力にする。

### 0:25 - 0:45 既存ツール観察 (ライブデモ)

- 一般公開されている「カメラレイアウトシミュレーター」のような既存ツールがあれば、画面を共有しながら触る。
- 観察観点は次の表を使う。

| 観点 | 見るポイント |
|---|---|
| 入力 | どんな情報を、どの順で入れさせているか |
| 可視化 | カメラ・被写体・画角の関係が直感的か |
| 出力 | 設置に持ち出せる情報になっているか |
| 編集 | 試行錯誤がやりやすいか |
| 学習コスト | 初見ユーザーが触れるか |

- 「真似したい点」「ワークショップ題材で改善したい点」をそれぞれ 3 つ書き出す。

### 0:45 - 1:05 ユーザーストーリー化

> **最短ルート**: ナビゲーターが VS Code Copilot Chat で **`sdd-guide`** カスタムエージェントに切り替え、ビジネスレビュアーから受け取った困りごとを 1 文だけ送信する。エージェントが US 3 本 → 仕様 → セルフレビュー → モック → 実装計画 まで順に進めるので、このセクション以降の手順は基本的に「OK / 修正 / スキップ」で応答するだけになる。詳細は `../docs/06-quickstart-flow.md` 参照。

「最短ルート」を使う場合は、以降のセッション (1:05 - 1:55) はそのまま `sdd-guide` の会話の中で進みます。スラッシュコマンドや個別エージェントを使う従来の進め方を続けたい場合は、以下の手順で進めてください。

- `exercises/01-user-stories.md` を全員で開く。
- 困りごとを 1 つ選び、ビジネスレビュアーが日常言葉で要望を述べる。
- ナビゲーターは VS Code Copilot Chat で **`/sdd-user-story`** を実行 (内部的に `../.github/prompts/sdd-user-story.prompt.md` を使う)。プロンプトを手で貼りたい場合は `../docs/03-copilot-prompts.md` の **7.2 ユーザーストーリー生成** で代替可能。
- 出力 3 本を `exercises/01-user-stories.md` に転記し、ビジネスレビュアーが価値の文言と受け入れ条件をその場で修正する。
- このターンで 1〜3 本のストーリーが揃えば OK。

### 1:05 - 1:25 Copilot で仕様化

- 1 本選んだストーリーに対して、**`/sdd-spec`** を実行する (手動コピペなら **7.3 仕様化** プロンプト)。
- 開発側はカスタムエージェントを **`spec-author`** に切り替えると、仕様外への発散を抑えられる。
- 出力された仕様をワークシート `exercises/02-spec.md` に貼り、開発レビュアーが「あいまいさ」「依存」「対象外の漏れ」を指摘する。
- 仕様確定と並行して、業務側は **`/sdd-mockup`** で `mockups/<slug>.html` を生成し、ブラウザで開いて感触を見ても良い (合意の質が上がる)。
- 3 ターン以内に仕様を確定させる。

### 1:25 - 1:35 休憩

- ここまでの成果を 1 枚で振り返る。

### 1:35 - 1:55 実装計画化

- **`/sdd-plan`** を使い、Next.js プロトタイプ前提のタスク分解を作る (手動コピペなら **7.4 実装計画化** プロンプト)。
- 出力を `exercises/03-implementation-plan.md` に貼る。
- 開発レビュアーが「30 分で作るなら何を削るか」を決める。
- 残ったタスクのうち実装する 1 件を **`/sdd-task`** に通し、Copilot Chat / Copilot Coding Agent に貼れる作業指示に整える。

### 1:55 - 2:25 プロトタイプ生成

- 開発ロールがカスタムエージェントを **`prototype-builder`** に切り替え、`/sdd-task` の出力を貼って 1 タスク実装する。
- 編集対象は `prototype/app/page.tsx` と `prototype/app/components/` が中心。`.github/instructions/prototype.instructions.md` が自動適用される。
- 30 分のうち、最初の 20 分は実装、残り 10 分は動作確認 (`npm run dev` で目視 + `npm run typecheck`) に充てる。

### 2:25 - 2:45 レビューと改善

- ビジネスレビュアーが実物を触ってフィードバックを口頭で出す。
- ナビゲーターはカスタムエージェントを **`business-reviewer`** に切り替えた上で **`/sdd-business-review`** を実行し、フィードバックを構造化する (手動コピペなら **7.5 レビュー / 改善** プロンプト)。
- 優先度 High の 1 件を、再度 `prototype-builder` モードで実装してその場で確認する。
- 時間が余れば、半自動ループ `copilot --agent .github/agents/spec-loop.agent.md ...` の挙動を 5 分だけ紹介する。

### 2:45 - 3:00 まとめ

- 以下を全員で 1 〜 2 行ずつ発言する。
  - 仕様駆動開発で良かった点
  - 詰まった点 / 改善したい点
  - 自分の現場に取り込むなら何から始めるか
- ファシリテーターは振り返りを `exercises/05-review.md` に貼る。

## 進行上の注意

- **完成を目指さない**。仕様、計画、実装、レビューの「型」を 1 周することを優先する。
- **ビジネスロールに必ず発言時間を作る**。Copilot のアウトプットがビジネス視点でレビュー可能か、という観点を毎セッションで確認する。
- **環境構築で詰まらない**。`prototype/` は `npm install` だけで動く構成にしてある。事前に各自が一度 `npm run dev` できる状態を作ってもらう。
- **過剰に作らせない**。1 プロンプトに 1 つの要求。Copilot に長い指示を投げて発散させない。

## コンティンジェンシー: GitHub Copilot のクォータが枯渇したら

UBB (Usage-Based Billing) により、180 分の途中で個人ごとの premium request 上限に達して Copilot が応答しなくなることがあります。バックアップとして **Microsoft Foundry (Azure OpenAI) の BYOK** を用意してあります。

### 事前準備 (主催者)

- 事前に `scripts/deploy-foundry-openai.sh` を実行し、Endpoint / API Key / Deployment Name を控えておく。
- 配布チャネルを決めておく (Teams プライベートチャットなどの非公開経路)。
- 詳細は `byok-setup.md` を参照。

### 切替の判断

- 1 名が「Copilot が応答しない」と申告 → その人だけ個別に切替を案内し、伴走する。
- 2 名以上に広がる / 同じセッションで複数発生 → 全員一斉切替を発表する。

### 全員切替の台本 (1 分)

> 全員、いったん手を止めてください。
> ここから Azure OpenAI に切り替えます。
> `docs/05-backup-byok.md` の手順 3 を見ながら、Endpoint / API Key / Deployment Name を入力してください。
> 切替が終わったらチャットで `/sdd-spec` を投げて応答が返ることを確認してください。
> 5 分後に再開します。

### 切替後の注意

- BYOK で切り替わるのは **チャット系のみ**。inline 補完は Copilot 標準のまま (上限超過時は止まる)。
- Copilot CLI で `spec-loop` / `mockup-builder` を動かしている場合、CLI 側は別系統。VS Code Copilot Chat の `/sdd-mockup` などで代替する。

### ワークショップ後

- 主催者は `scripts/teardown-foundry-openai.sh` を実行してリソースを削除する。
- 参加者には「VS Code から追加した Azure プロバイダー設定を削除してください」と案内する。
